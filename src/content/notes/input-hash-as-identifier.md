---
title: "成果物を材料のハッシュで識別すると、作成済みかどうかがハッシュを調べるだけで分かり、中身が変わらないので長くキャッシュできる"
date: 2026-11-03
tags: [programming]
---

材料を入れると時間のかかる処理を経て成果物が出てくる仕組みで、同じ材料からは必ず同じ成果物ができるとする。このとき、成果物の名前（識別子）を材料のハッシュにしておくと便利だ。作成済みかどうかがすぐ分かり、配信先でも安心して長くキャッシュできる。

主な利点は3つある。

- **作り直しを省ける**: 材料のハッシュを計算して、その名前の成果物がすでにあれば処理を飛ばす。新しい材料の組み合わせのときだけ作ればよい。何度実行しても結果は同じ（冪等）で、コストは新しい分だけで済む。
- **キャッシュを無期限にできる**: 名前が同じなら中身も必ず同じなので、配信先のキャッシュは古くなることがない。材料が変われば名前も変わるので、更新後は新しい名前で取りに来る。キャッシュの期限を短くして鮮度を保つ必要がない。古い成果物が残り続ける問題は、今の上流から参照されていないものを消す仕組み（ガベージコレクション）を別に用意すれば片づく。
- **名前を受け渡さなくてよい**: 材料からハッシュを作る手順さえ上流と下流で共有しておけば、下流は自分で名前を計算できる。成果物ごとに名前を伝える必要がない。

実際によく使われている場面もある。

| 場面 | 材料 | 成果物 |
| --- | --- | --- |
| CI の依存関係のキャッシュ | ロックファイル | インストール済みの `node_modules/` など |
| Nix のパッケージ | ソース・依存先・ビルド手順のすべて | `/nix/store/<ハッシュ>-名前` に置かれるパッケージ |
| Bazel や Turborepo のビルドキャッシュ | 入力ファイルとコマンド | ビルドの出力 |

```yaml
# GitHub Actions: ロックファイルが変わらない限り同じキャッシュを使う
- uses: actions/cache@v4
  with:
    path: ~/.npm
    key: npm-${{ hashFiles('package-lock.json') }}
```

なお、Vite などが出力するファイル名の `index-a1b2c3.js` のハッシュは、材料ではなく成果物そのものの中身から計算している。成果物を作ってからでないと名前が決まらないが、長くキャッシュできるという利点は同じだ。

注意点は、何を材料に含めるかだ。「この部分はずっと変わらないだろう」と材料から外すと、後でそこを変えたときに、違う成果物に同じ名前が付いてしまう。古い成果物が使われ続け、しかも気づきにくい。ツールのバージョンや設定のように見落としやすいものも含めて、「これが全部同じなら、成果物は絶対に同じと言える」ところまで洗い出してから材料を決める。また、同じ材料から同じハッシュが出るように、材料を並べる順番や書式も決めておく。
