---
title: "VPC はリージョン、サブネットは AZ に属し、ルートテーブルの local ルートのおかげで VPC の中は AZ をまたいで通信できる"
date: 2026-11-21
tags: [aws, network, routing]
---

VPC はリージョンに属するリソースで、AZ には縛られない。サブネットは1つの AZ に属する。ルートテーブル（RT）は AZ に属さない VPC 全体のリソースで、どの RT にも消せない `local` ルートがあるので、VPC の中では AZ を気にせず通信できる。

東京に VPC を2つ、大阪に1つ作る、という形で VPC はリージョンごとに作る。VPC の中にはサブネットを作り、1つの AZ に複数のサブネットを置いてもよい。たとえば、AZ-a にサブネット1・2、AZ-b にサブネット3・4 を置いた VPC が考えられる。

RT は1つの VPC にいくつでも作れて、各サブネットは、そのうちちょうど1つの RT を参照する。

| RT | ルート | 参照するサブネット |
| --- | --- | --- |
| RT1 | `0.0.0.0/0 → IGW` | サブネット1・3 |
| RT2 | `0.0.0.0/0 → NAT Gateway` | サブネット2・4（EC2 を置く） |

参照する RT の `0.0.0.0/0` が IGW（Internet Gateway）を向いているサブネットをパブリックサブネット、そうでないサブネットをプライベートサブネットと呼ぶ。どの RT を参照するかが、サブネットの性質を決める最も重要な要素になる。

どの RT にも、「VPC の CIDR → `local`」という行が必ずあり、消すことはできない。`local` は VPC そのものを指し、この行にマッチしたパケットは VPC の中で AWS が届けてくれる。だから、別の AZ のサブネットとも、ルートを書き足さずに通信できる。ロンゲストマッチなので、これより細かいルートを書いて上書きすることもできる。ただ、そうする場面は、Network Firewall のような検査を間にはさみたいときくらいしかない。

VPC の外のリソースと通信するときは、相手が VPC にどう入ってくるかで、AZ の扱いが3つのパターンに分かれる。

| パターン | 例 | AZ の扱い |
| --- | --- | --- |
| ENI を持たない | IGW、ゲートウェイ型 VPC エンドポイント | VPC 全体のリソース。参照する RT にルートがあれば、どのサブネットからでも使える |
| ENI を持ち、AZ をまたいでも使える | インターフェース型 VPC エンドポイント、NAT Gateway | ENI は1つのサブネット（AZ）に置かれるが、`local` ルートで届くので、別の AZ からも使える |
| ENI を持ち、同じ AZ からしか使えない | Transit Gateway の VPC アタッチメント | ENI と同じ AZ のサブネットからしか使えないので、AZ ごとにサブネットを用意して ENI を置く |

2つ目のパターンのインターフェース型 VPC エンドポイントは、RT にルートを書く必要もない。ENI の IP アドレスは VPC の CIDR に含まれるので、`local` ルートで届く。サービスの DNS 名がこの ENI の IP アドレスに解決されるようにしておけば、そのまま使える。とはいえ、AZ の障害に備えるなら、2つ目のパターンでも AZ ごとに ENI を置くのが推奨される。3つ目のパターンでは、AZ ごとに ENI を置くことが必須になる。
