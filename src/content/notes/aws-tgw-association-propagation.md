---
title: "Transit Gateway のルートテーブルとアタッチメントの関係は2つあり、association はパケットをどの表で引くか、propagation は経路をどの表に自動で書き込むかを決める"
date: 2026-11-21
tags: [aws, network, routing]
---

Transit Gateway（TGW）は、つながっている接続口（アタッチメント）の間でパケットを中継するハブで、どう中継するかを TGW のルートテーブル（RT）が決める。アタッチメントと RT の関係には association と propagation の2つがあり、association は「そのアタッチメントから来たパケットをどの RT で引くか」、propagation は「そのアタッチメントへの経路をどの RT に自動で書き込むか」を決める。対になる概念ではなく、役割の違う別々の設定である。

同じリージョンに VPC がたくさんあるとき、VPC ピアリングには推移性がないので、全部を互いにつなぐにはフルメッシュにするしかなく、ピアリングの数は $O(N^2)$ で増える。オンプレとも DX や VPN でつなぎたいとなればなおさらで、そこで TGW を使う。TGW はリージョンのリソースで、VPC と違い、1つのアカウントの1つのリージョンにふつうは1つだけ置く（本番と開発で影響範囲を分けたいときなどに複数にすることもある）。

TGW の RT は、VPC の RT とはまったく別のもの。TGW にとって VPC は、つながる相手の1つにすぎない。

- **association**: 1つのアタッチメントが関連付けられる RT は最大1つ。アタッチメントから TGW に入ったパケットは、その RT を引いて、出ていくアタッチメントが決まる。どの RT にも関連付けられていないアタッチメントから来たパケットは、引く表がないので捨てられる。VPC のメインルートテーブルのような代わりの表はない。TGW の「デフォルトの関連付け先 RT」は、アタッチメントを作ったときに自動で association する機能であって、代わりの参照先ではない。
- **経路**: RT の経路は、propagation で自動で入れるか、スタティックで書く。ロンゲストマッチで、プレフィックスの長さが同じならスタティックが優先される。TGW 同士のピアリングアタッチメントは propagation できないので、スタティックで書くしかない。
- **propagation**: アタッチメント att2 から RT1 への propagation を有効にすると、RT1 に「att2 の先にある CIDR → att2」が自動で入る。

att1 が RT1 に association され、RT1 に att2 が propagation されていれば、att1 から att2 には届く。ただし、その返事が届くかどうかは別の問題で、att2 が association されている RT に att1 への経路があるかで決まる。ここがそろっていないと、片方向にしか届かない。

デフォルトでは RT が1つ自動で作られ、すべてのアタッチメントがその RT に association も propagation もされる。だから何も考えなくても、TGW はすべてのアタッチメントを互いにつなぐハブになる。便利な反面、全部が全部とつながってしまう。アクセスを制御したいなら、自動の association と propagation を無効にして、RT を複数用意する。たとえば「att1 と att2 は互いに通信でき、att3 はそれらから切り離すが、全員が att4 には行ける」ようにしたいなら、次のようにする。

| RT | association するアタッチメント | propagation するアタッチメント |
| --- | --- | --- |
| RT-A | att1、att2 | att1、att2、att4 |
| RT-B | att3 | att4 |
| RT-C | att4 | att1、att2、att3 |
