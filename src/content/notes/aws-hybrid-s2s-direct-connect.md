---
title: "AWS のハイブリッドクラウドは VPC を社内 WAN の拠点の1つとしてつなぐ構成で、Site-to-Site VPN か Direct Connect で経路を作る"
date: 2026-11-15
tags: [aws, network, vpn]
---

ハイブリッドクラウドは、東京本社・大阪支社と同じ並びに「AWS の VPC A」を加え、VPC を社内 WAN の拠点の1つとして扱う構成。社内から見ても VPC から見ても、相手はふつうの LAN の1つに見えるようにする。そのため、VPC の CIDR は社内のどの CIDR とも重複しないように分けておく必要がある。

いちばん手軽なのは、インターネット上に VPN を張って経路にする方法で、AWS では **Site-to-Site VPN（S2S）** を使う。ただ、VPC は仮想的なネットワークなので、オンプレのように「ルーターの差込口に挿せば終わり」というわけにはいかない。そこで **VGW（仮想プライベートゲートウェイ）** を VPC にアタッチし、S2S は VGW を終端にして VPC につなぐ。経路の教え方は、スタティックルーティングか、双方を AS とみなした BGP のどちらか。BGP なら両側に AS 番号を用意する。スタティックでも成り立つのは、VPN のトンネル自体が相手の生死を判断する役割を担えるからだ。

VPN はインターネットの混雑の影響を受けるので、専用線を使いたいなら **Direct Connect（DX）** になる。自社の拠点から、AWS が各地に置いている物理的な拠点「DX ロケーション」まで専用線を引き、そこから目的のリージョンまでは AWS のバックボーンで運ばれる。高額で、工事に数週間〜数か月かかる本格的なものだが、ガバナンスの面で説明しやすいといった利点もある。

S2S なら VPN をいくらでも増やせるが、DX の物理線を接続先ごとに引くのは現実的でない。そこで1本の線を VLAN で論理的に分け、それぞれで BGP を使って経路を交換する。この VLAN と BGP の組が **VIF（仮想インターフェース）** で、つなぐ先によって種類がある。

| VIF | つなぐ先 |
| --- | --- |
| Private VIF | VPC の VGW（または DXGW） |
| Public VIF | S3 など、VPC の中にない AWS のパブリックなサービス |
| Transit VIF | DXGW を介した Transit Gateway（多数の VPC） |

DX ではスタティックは使えず、BGP が必須になる。VPN と違って線そのものには相手の生死を確かめる仕組みがないので、BGP のやり取りでそれを判断することになる。

多くの VPC に DX でつなぎたいときは、**DXGW（Direct Connect ゲートウェイ）** をはさみ、そこから各 VPC の VGW につなぐ。間違えやすいが、DXGW がつなぐのはオンプレと各 VPC の間だけで、DXGW 経由で VPC 同士が通信できるわけではない。VPC 同士もつながるハブがほしいなら **TGW（Transit Gateway）** を使う。

DX の物理線が1本だけでは SPOF になるので、冗長化は、高額だが DX をもう1本引くか、待機系を S2S にするかのどちらかが多い。
