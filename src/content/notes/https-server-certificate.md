---
title: "HTTPS は暗号化だけでなく相手が本物のサーバーかも確かめ、それを保証するのが認証局の発行するサーバー証明書"
date: 2026-10-17
tags: [security, http]
---

HTTPS（TLS）がしていることは、通信の暗号化だけではない。通信相手が本物のサーバーであることの確認と、途中で改ざんされていないことの確認もしている。このうち、相手が本物のサーバーであることを保証するのがサーバー証明書。証明書は、サーバー自身ではなく、第三者の認証局（CA）が発行する。

| 目的 | 防ぐもの | 主な仕組み |
| --- | --- | --- |
| 暗号化（機密性） | 盗聴 | 共通鍵暗号 |
| 改ざんの検知（完全性） | 途中での書き換え | メッセージ認証コード |
| サーバーの認証（真正性） | なりすまし | サーバー証明書 |

暗号化だけでは足りない。攻撃者が偽のサーバーを立て、利用者がそこにつないでしまえば、通信は暗号化されていても中身は攻撃者に筒抜けになる。そこで、つないだ相手が、本当にそのドメインのサーバーかを確かめる必要がある。サーバーが自分で「本物です」と名乗っても意味がないので、利用者が信頼している認証局に保証してもらう。

サーバー証明書には、ドメイン名とサーバーの公開鍵が書かれていて、認証局がそこに署名している。ブラウザーは次の2つを確かめる。

1. 証明書の署名をたどり、自分が最初から信頼しているルート認証局まで行き着くか
2. 接続中のサーバーが、証明書の公開鍵に対応する秘密鍵を持っているか

証明書自体は誰でも手に入れられる公開の情報なので、2 の確認が欠かせない。秘密鍵を持っていない偽のサーバーは、証明書をコピーしても本物になりすませない。

認証局は、証明書を発行する前に、申請者がそのドメインを本当に管理しているかを確かめる（ドメイン認証）。主な方法は次のとおり。

| 方法 | 申請者がすること |
| --- | --- |
| DNS | 認証局が指定した値を、そのドメインの DNS レコードに登録する |
| HTTP | 認証局が指定したファイルを、そのドメインの Web サーバーの決まった場所に置く |
| メール | そのドメインの管理者用アドレス（admin@ など）に届いたメールで承認する |

DNS で確かめる場合、使うレコードの種類はサービスによって違う。Let's Encrypt などの ACME という方式では TXT レコードを使う。AWS Certificate Manager では CNAME レコードを使う。どちらの場合も、DNS を書き換えられるのはドメインの管理者だけ、という点を根拠にしている。

なお、ドメインの管理を確かめるだけの証明書は DV 証明書と呼ばれ、運営している組織までは保証しない。組織の実在まで確かめるものに、OV 証明書や EV 証明書がある。
