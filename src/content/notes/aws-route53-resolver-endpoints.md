---
title: "VPC の DNS（Route 53 Resolver）は VPC の中からしか引けないので、オンプレミスと名前解決し合うにはインバウンドとアウトバウンドのエンドポイントを置く"
date: 2026-11-22
tags: [aws, dns, network]
---

VPC には、CIDR のネットワークアドレスに 2 を足したアドレスで DNS が用意されている。これを Route 53 Resolver と呼び、アドレスから VPC CIDR+2 と呼ぶこともある。答えるのは同じ VPC の中からの問い合わせだけなので、オンプレミスと名前解決し合うには、VPC の中にインバウンドエンドポイントとアウトバウンドエンドポイントを置く。

Route 53 Resolver は、インターネットの FQDN を解決するほか、その VPC に関連付けた Route 53 のプライベートホストゾーンの名前も解決する。Resolver は VPC ごとに別々にあるわけではなく、リージョンで動く1つのサービスで、各 VPC の +2 はその入り口にすぎない。どこかに DNS サーバーが1台立っているわけでもなく、EC2 から +2 に問い合わせると、インスタンスが載っているホスト側でその場で処理されて答えが返る。そのため、VPC の外から +2 に問い合わせても答えは返らない。

DX や S2S VPN でオンプレミスと VPC がつながっていれば、IP アドレスを指定してのアクセスはすでにできる。FQDN で引き合うには、向きごとにエンドポイントを用意する。どちらも VPC の中に置く ENI として作る。

| 向き | 使うもの | 設定 |
| --- | --- | --- |
| オンプレミス → VPC の名前 | インバウンドエンドポイント | オンプレミスの DNS で、VPC 側のドメインの問い合わせをエンドポイントの IP アドレスへ転送する |
| VPC → オンプレミスの名前 | アウトバウンドエンドポイント | 転送ルールで、`fileserver.example.local` のような社内ドメインの問い合わせを、エンドポイント経由でオンプレミスの DNS へ送る |

VPC がたくさんあると、エンドポイントを VPC ごとに作るのは手間で、ENI ごとに料金もかかる。そこで、DNS 用の VPC を1つ作って、エンドポイントはそこにだけ置く構成がある。

これが成り立つのは、Resolver が1つのサービスだから。

- **アウトバウンド**: オンプレミスの DNS を `192.168.0.53` とすると、「`corp.example.local` は `192.168.0.53` へ、DNS 用 VPC のアウトバウンドエンドポイントから送る」という転送ルールを作り、RAM で共有して各 VPC に関連付ける。各 VPC がするのは、いつもどおり +2 に問い合わせて答えを受け取ることだけ。Resolver は、その VPC にこのルールが関連付けられているのを見て、DNS 用 VPC のアウトバウンドエンドポイントからオンプレミスへ問い合わせを送る。各 VPC の問い合わせパケットが DNS 用 VPC まで運ばれるわけではないので、各 VPC と DNS 用 VPC の間に TGW などの経路は要らない。共有するのもエンドポイントではなくルールになる。
- **インバウンド**: オンプレミスからの問い合わせは、DNS 用 VPC のインバウンドエンドポイントで受けて、その場で答える。そのためには、各 VPC が使っているプライベートホストゾーンを DNS 用 VPC でも引ける必要がある。そこで、それらのプライベートホストゾーンを DNS 用 VPC にも関連付けておく。
