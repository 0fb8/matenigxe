---
title: "DNSSEC は DNS の応答に署名を付け、親ゾーンの DS レコードをたどって鍵の正しさを確かめる"
date: 2026-10-08
tags: [network, dns, security]
---

DNSSEC では、権威 DNS サーバーが返すレコードにデジタル署名を付ける。フルサービスリゾルバはその署名を検証して、応答が途中で改ざんされていないかを確かめる。偽の応答をキャッシュに入れさせるキャッシュポイズニングへの対策になる。

DNSSEC で使う主なレコードは次のとおり。

| レコード | 役割 |
| --- | --- |
| RRSIG | A レコードなどに付ける署名 |
| DNSKEY | そのゾーンの公開鍵。RRSIG の検証に使う |
| DS | 子ゾーンの DNSKEY のハッシュ。**親ゾーン**に置く |

DNSKEY 自体が偽物だったら、署名を検証しても意味がない。そこで、親ゾーンにある DS レコードと突き合わせて、子ゾーンの DNSKEY が本物かを確かめる。DS レコードも親ゾーンの鍵で署名されているので、`example.com` → `com` → ルートと上にたどっていける。最後はリゾルバにあらかじめ設定してあるルートゾーンの鍵（トラストアンカー）にたどり着く。この「信頼の連鎖」は、ルート証明書までたどる TLS 証明書のチェーンと考え方が似ている。

```sh
# 署名（RRSIG）も一緒に表示する
dig +dnssec example.com A
```

DNSSEC で通信が暗号化されると思いがちだが、DNSSEC が保証するのは改ざんされていないことと、正しいゾーンから来た応答であることだけ。問い合わせの中身は暗号化されない。暗号化したいなら DoT（DNS over TLS）や DoH（DNS over HTTPS）を使う。

署名や鍵が加わると、応答が大きくなる。もともと UDP の DNS メッセージは 512 バイトまでだったので、DNSSEC には EDNS0 が欠かせない。EDNS0 は、より大きな UDP メッセージを受け取れることを伝えるための拡張。それでも収まらないときは、応答に「切り詰めた」という印（TC ビット）が付き、リゾルバは TCP の 53 番ポートで問い合わせ直す。
