---
title: "Transit Gateway の VPC アタッチメントは AZ ごとに ENI を置き、VPC から Transit Gateway に乗れるのは ENI と同じ AZ のリソースだけ"
date: 2026-11-21
tags: [aws, network, routing]
---

Transit Gateway（TGW）に VPC をつなぐときは、VPC アタッチメントを作り、AZ ごとにサブネットを1つずつ指定する。AWS はそのサブネットに ENI を置き、VPC のリソースはその ENI から TGW に乗る。VPC の中は `local` ルートのおかげで AZ を気にせず通信できるが、TGW に乗るときは、ENI と同じ AZ のリソースしか乗れない。

アタッチメントは TGW 側のリソース、ENI は VPC 側に置かれる実体、という二層になっている。1つの VPC アタッチメントは、指定した AZ の数だけ ENI を持つ。ENI がない AZ のリソースは TGW に乗れないので、リソースを置いている AZ にはすべて ENI を置く必要がある。逆に、TGW から VPC に降りる向きは、ENI のある別の AZ に回して届けてくれる。この向きによる違いのせいで、「行きは届くのに返事が戻らない」という症状が起きる。

ENI を置くサブネットは、AZ の中のどれでもよい（ただし AZ ごとに1つ）。それでも実際には、AZ ごとに ENI 専用の小さなサブネット（`/28` が多い）を作ることが多い。理由は2つある。

- 業務用のサブネットに置くと、その IP アドレスを消費する。
- TGW から VPC に入ってきたパケットが最初に従うのは、ENI があるサブネットの RT。そこを業務用のサブネットの RT と分けて制御したい。

TGW の RT だけでなく、VPC の RT にも経路が必要になる。VPC-A のサブネットの RT に「VPC-B の CIDR → TGW」がなければ、パケットはそもそも TGW に向かわない。VPC-A から VPC-B に届けるには、次の3つすべてに経路が必要で、返事のためには逆向きにも同じだけ必要になる。

1. VPC-A のサブネットの RT
2. TGW の RT（VPC-A のアタッチメントに association されたもの）
3. VPC-B のサブネットの RT

もう1つ、TGW には **AZ アフィニティ** という性質がある。VPC-A の AZ-a の ENI から TGW に入ったパケットは、VPC-B でも AZ-a の ENI から出ていく。VPC-B に AZ-a の ENI がなければ、ENI のある AZ のどれかに送られ、そのフローの間はその AZ に固定される。できるだけ同じ AZ の中で済ませれば、レイテンシも AZ 間の通信も減り、AZ の障害の影響も広がりにくい。

これが問題になるのは、ステートフルなファイアウォールを1つの検査用 VPC に集めた構成だ。行きと帰りで別の AZ のファイアウォールを通ると、ファイアウォールは片方向しか見られず、通信を落としてしまう。そこで、検査用 VPC のアタッチメントで **アプライアンスモード** を有効にし、フローごとに通る AZ を固定する。
