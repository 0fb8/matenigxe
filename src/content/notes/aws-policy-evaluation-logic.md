---
title: "AWS のリクエストは明示的な Deny が最優先で、SCP や許可境界などのガードレールが範囲を絞り、Allow を出せるのはアイデンティティベースとリソースベースのポリシーだけ"
date: 2026-11-24
tags: [aws, security]
---

AWS でリクエストを許可するかどうかは、決まった手順で機械的に判定される。どこか1つのポリシーにでも明示的な Deny があれば、ほかに何が書かれていても拒否になる。一方で、Allow が1つあるだけでは許可になるとは限らない。

これは、ポリシーに役割の違う2種類があるから。

| 種類 | ポリシー | 役割 |
| --- | --- | --- |
| ガードレール | SCP、RCP、許可境界、セッションポリシー | できることの上限を決める。これだけでは何も許可しない |
| 実際に許可するもの | アイデンティティベースポリシー、リソースベースポリシー | 実際に Allow を出す |

ガードレールは、どれか1つでも許していなければ拒否になる。逆に、ガードレールが全部許していても、アイデンティティベースかリソースベースのポリシーが Allow を出していなければ、何も許可されていないので拒否になる（暗黙の Deny）。

それぞれのガードレールは、次のような範囲を絞る。

- SCP（Service Control Policy）: Organizations で、組織のプリンシパル（IAM ユーザーやロール）ができることの上限を一括で決める
- RCP（Resource Control Policy）: Organizations で、組織のリソースに対してできることの上限を一括で決める。たとえば「組織の S3 バケットには組織の外からアクセスさせない」のように使う
- 許可境界（Permissions Boundary）: IAM ユーザーやロールに付けて、そのプリンシパルが持てる権限の上限を決める。開発者に IAM ロールを作らせたいとき、「作るロールには必ずこの許可境界を付ける」という条件を付けておくと、開発者は許可境界より強いロールを作れない
- セッションポリシー: ロールを引き受けるときなどに渡して、その一時的なセッションの権限をさらに絞る

アイデンティティベースとリソースベースのどちらの Allow が要るかは、アカウントの関係で変わる。

- 同じアカウントの中なら、どちらか片方が Allow を出していればよい
- クロスアカウントなら、両方が Allow を出している必要がある

ただし、KMS のキーポリシーと IAM ロールの信頼ポリシーは、同じアカウントの中でもリソース側のポリシーで許可しておく必要がある。アイデンティティベースのポリシーだけでは使えない。
