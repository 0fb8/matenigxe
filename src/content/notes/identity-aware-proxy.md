---
title: "IAP は IAM と連携してアプリごとにアクセスを判断するプロキシで、VPN の内側なら全部許すやり方と違い横移動されにくい"
date: 2026-10-21
tags: [security, vpn, zero-trust]
---

IAP（Identity-Aware Proxy）は、利用者と社内のアプリの間の通信経路に置かれるプロキシ。IAM と連携して「誰が」「どのアプリに」アクセスしようとしているかを確かめ、アプリごとに通すかどうかを決める。

従来のリモートアクセスでは、VPN で社内ネットワークにつなぎ、つながった後は社内のどのシステムにも届く、というやり方が多かった。IAP では、利用者は社内ネットワークには入らない。アプリにアクセスするたびに IAP が IAM に問い合わせて、その人がそのアプリを使ってよいかを判断し、許可された通信だけを中継する。

| | VPN | IAP |
| --- | --- | --- |
| つながる範囲 | 社内ネットワーク全体 | 許可されたアプリだけ |
| 判断の単位 | VPN に入れるかどうか | アプリへのアクセスごと |
| 判断の材料 | VPN の認証 | IAM の ID や端末の状態など |

この違いから、IAP には次のような利点がある。

- **横移動されにくい**: アプリごとに許可を分けているので、仮にアカウントが乗っ取られても、攻撃者はそのアカウントに許されたアプリにしか届かない。VPN のように、入り込んだところから社内の別のシステムへ次々に広げていくことが難しい。
- **ファイアウォールに穴をあけなくてよい**: VPN では、外からの接続を受け付けるために VPN 装置を公開し、その分ファイアウォールの受信を許可する必要がある。IAP ではその必要がない（仕組みは下で説明する）。
- **柔軟に使える**: 多くはクラウドサービスとして提供されるので、利用者や拠点が増えても VPN 装置のように通信が1か所に集中しにくく、設定の変更もしやすい。

穴をあけなくてよいのは、社内のアプリをクラウドの IAP で守る場合、次のような構成になることが多いため。

```
[利用者] ──▶ [IAP（クラウド）] ◀── [コネクタ] ──▶ [社内アプリ]
                               │
                         ファイアウォール
```

社内に置いたコネクタが、自分からクラウドの IAP へ接続を張っておく。IAP は許可したリクエストだけを、その接続を使って社内へ流す。ファイアウォールから見ると、どちらも「内から外へ」張った接続の上の通信なので、外から内への受信を許可しなくて済む。社内のアプリはインターネットから直接見えないので、攻撃者が狙う入り口もなくなる。なお、アプリ自体がクラウドにある場合は、IAP がアプリの前に直接置かれ、コネクタを使わないこともある。

IAP は、ゼロトラストの「社内かどうかではなく、アクセスのたびに確かめる」という考え方を、リモートアクセスの場面で形にしたものといえる。
