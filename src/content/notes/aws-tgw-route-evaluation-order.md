---
title: "Transit Gateway の RT はロンゲストマッチ、static、アタッチメントの種類、AS_PATH の順で経路を選ぶので、DX の予備にする VPN は BGP で propagation させる"
date: 2026-11-22
tags: [aws, routing, redundancy]
---

Transit Gateway（TGW）の RT に同じ宛先の経路がいくつもあるときは、決まった順に比べて1つを選ぶ。順番は、ロンゲストマッチ、static か propagation か、アタッチメントの種類、BGP の AS_PATH の長さ。前の段階で差がつけば、後ろの段階は見ない。

| 順 | 比べるもの | 優先されるほう |
| --- | --- | --- |
| 1 | プレフィックスの長さ | 長いほう（ロンゲストマッチ） |
| 2 | 経路の入り方 | static（VPN の static ルートも含む）が propagation より上 |
| 3 | アタッチメントの種類（propagation の経路どうし） | VPC → DX Gateway → Connect → VPN の順 |
| 4 | AS_PATH | 短いほう |
| 5 | それでも同じなら | ECMP を有効にしていれば両方に振り分ける |

ピアリングアタッチメントは propagation できず static で書くので、3の比較には出てこない。

順番が効いてくる典型例が、オンプレミスと TGW を DX Gateway（主系）と Site-to-Site VPN（待機系）でつなぐ冗長構成。3の段階で DX Gateway が VPN より上なので、両方を propagation で入れておけば、ふだんは DX が選ばれる。ところが VPN を static ルーティングで作ると、その経路は TGW の RT に static として入る。すると2の段階で DX の propagation の経路に勝ってしまい、ふだんから VPN が使われる。DX を主系にしたいなら、VPN は BGP（動的ルーティング）で作り、propagation で入れる。

DX を2本引いてどちらも DX Gateway から入ってくるときなど、同じ種類のアタッチメントから同じ宛先が来ると、比較は4の AS_PATH まで進む。たとえば東京と大阪に1本ずつ引いていて、AWS から社内への通信を東京側に寄せたいなら、大阪側で広告する経路に AS_PATH プリペンドをかけて長く見せる（DX の冗長化の記事も参照）。逆に言えば、AS_PATH が比べられるのはここまで差がつかなかったときだけなので、それより前の段階で決まる構成ならプリペンドは効かないし、要らない。

最後まで同じなら、ECMP（Equal-Cost Multi-Path）を有効にしていれば、複数の経路に通信を振り分ける。振り分けはフロー単位で、1つのフローは1本の経路だけを通る。そのため1つの通信が速くなるわけではなく、全体として流せる量が増える。この点はリンクアグリゲーションと同じだが、ECMP は複数の経路をルーティングで使い分けるもので、リンクを1本に束ねるわけではない。
