---
title: "メールは閉じたネットワークで性善説のもとに生まれたので送信元をいくらでも偽れ、後から SPF・DKIM・DMARC で補っている"
date: 2026-10-11
tags: [network, mail, security]
---

メールの送信元は、ヘッダーの From もエンベロープ From も、送信者が好きに書ける。メールは、限られた人しか使わないネットワークで、相手を信用する前提（性善説）で作られたからだ。この仕組みは今も変わっていないので、なりすましを防ぐ認証の仕組みを後から足している。

メールは Web より古い。ネットワーク上でのメールは 1971 年ごろに ARPANET で始まり、SMTP は 1982 年に定められた。Web が生まれたのは 1990 年前後だ。当時のインターネットは、研究機関や軍に関係する組織をつなぐ、閉じたネットワークだった。使うのは身元の分かる人ばかりなので、送信元が本物かを確かめる仕組みは入らなかった。

SMTP では、送信元のアドレスは送信者が書いた値をそのまま使う。

```text
MAIL FROM:<ceo@example.com>       ← 誰でも書ける
DATA
From: 社長 <ceo@example.com>      ← これも誰でも書ける
```

受け取るサーバーは、この値が本当かを SMTP の中では確かめない。そのため、銀行や取引先を名乗るフィッシングメールが簡単に作れてしまう。

送信時の SMTP 認証（MSA でのユーザー認証）があるから防げる、と思いがちだが、そうではない。あれは「自分のメールサーバーを使ってよい人か」を確かめるだけで、「From に書いたアドレスがその人のものか」までは確かめない。さらに、なりすましをする人は、自分で用意したサーバーから相手の MTA へ直接送ればよい。

そこで、受け取る側が送信元を確かめるための仕組みが、後から作られた。

| 仕組み | 何を確かめるか（大まかに） |
| --- | --- |
| SPF | 送ってきたサーバーの IP アドレスが、そのドメインから送ってよいサーバーとして登録されているか |
| DKIM | メールに付いた電子署名が、そのドメインの鍵で正しく検証できるか |
| DMARC | SPF や DKIM で確かめたドメインが、ヘッダーの From と一致するか。失敗したらどう扱うか |

どれも、SMTP そのものを作り直すのではなく、DNS にドメインの情報を公開しておき、受信側がそれを照らし合わせるという足し算の形になっている。それぞれの仕組みは、別の記事で扱う。
