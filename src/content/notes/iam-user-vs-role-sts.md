---
title: "IAM ユーザーは長期の認証情報を持つ「その人そのもの」で、IAM ロールは IdP の認証をもとに STS が発行する一時認証情報で引き受けるもの"
date: 2026-11-25
tags: [aws, security]
---

IAM ユーザーと IAM ロールはまったく別のもの。IAM ユーザーは、IAM の中に作る「その人そのもの」で、長期の認証情報を持つ。IAM ロールは長期の認証情報を持たず、誰かが一時的に引き受けて使う権限のまとまり。

IAM ユーザーは、ID の管理も認証も IAM 自身が行う。フェデレーションの言葉でいえば、IdP と SP を IAM が一人二役でこなしている形。認証にはパスワードや、アクセスキーとシークレットアクセスキーの組を使う。これらは期限のない長期の認証情報なので、漏れると無効にするまで使われ続ける。

IAM ロールを使うときは、AWS STS（Security Token Service）が一時認証情報を発行する。STS は IdP などの認証結果を信頼し、ロールの信頼ポリシーで許されていれば、一定時間だけ使える認証情報を返す。STS には、何で認証してきたかに応じた API がある。

| API | 何をもとに発行するか |
| --- | --- |
| `AssumeRole` | IAM ユーザーや別のロールの認証情報 |
| `AssumeRoleWithSAML` | SAML の IdP が発行したアサーション |
| `AssumeRoleWithWebIdentity` | OIDC の IdP が発行した ID トークン |
| `GetSessionToken` | IAM ユーザーの認証情報（ロールは引き受けず、その IAM ユーザー自身の一時認証情報を返す。MFA と組み合わせて使う） |

一時認証情報は、アクセスキー、シークレットアクセスキー、セッショントークンの3つの組。アクセスキーは、IAM ユーザーの長期のものが `AKIA`、一時的なものが `ASIA` で始まるので見分けられる。AWS の API リクエストはアクセスキーとシークレットアクセスキーで署名する仕組みなので、一時認証情報もその形をそろえたうえで、セッショントークンを添えて有効なセッションであることを示す。

いまの推奨は、そもそも IAM ユーザーを作らず、人のアクセスもすべて一時認証情報で行うこと。IAM ユーザーでログインしてからロールに切り替えるのではなく、ID の管理は IdP に任せ、AWS 側はロールだけを持つ。AWS では IAM Identity Center がこの役を担い、ユーザーは複数のアカウントのロールを一時認証情報で使える。Identity Center のユーザーは IAM ユーザーとは別のもので、ID は Identity Center 自身のディレクトリのほか、Active Directory や Okta などの外部の IdP に置くこともできる。Active Directory を使うときは、AWS Directory Service でつなぐ。
