# 長めの記事を書く

ユーザーが考えたこと・知ったことを、見出しのある長めの記事として1本にまとめる。分量が違うだけで、`/note` の短い記事の延長にあたる。一覧では印が付き、「長めの記事」のページ（`/long/`）にも並び、記事ページには目次が付く。

ユーザーの入力: $ARGUMENTS

## `/note` との違い

| | `/note` | `/longnote` |
| --- | --- | --- |
| 長さ | 400〜1000 字 | 上限なし |
| 見出し | 原則使わない | `##`・`###` を使う（目次になる） |
| 分け方 | 1記事1トピック | 分割しない。入力全体で1本 |
| ユーザーの構成 | ふつうの解説に寄せてよい | 基本の構成は尊重する（下の「書き方」） |
| frontmatter | | `long: true` を付ける |

## 手順

1. **入力の状態を見て、進め方を決める**
   - **文章として整っている場合**: 構成案は出さずに、そのまま手順 2 へ進む。
   - **断片的なメモの場合**: 先に構成案（見出しの並びと、それぞれで何を書くかを1行ずつ）を見せて、合意してから書く。聞きたいことがあれば、同じメッセージで最大2〜3個まとめて聞く。

2. **既存の記事とタグを確認する**（`/note` と同じコマンド）
   ```sh
   grep -h '^tags:' src/content/notes/*.md | tr -d '[]' | sed 's/^tags://' | tr ',' '\n' | sed 's/^ *//;s/ *$//' | grep -v '^$' | sort | uniq -c | sort -rn
   grep -H '^title:' src/content/notes/*.md
   ```
   - 関連する既存の記事があれば、本文の中でその概念に触れておく（リンクは張らなくてよい）。

3. **記事を書く**
   - `npm run new -- --long <slug> "<タイトル>"` でファイルを作り、本文と tags を書き込む。
   - `npm run build` を実行して成功することを確かめる。失敗したら直す。

4. **commit する（push はしない）**
   ```sh
   git add src/content/notes/<slug>.md
   git commit -m "longnote: <タイトル>"
   ```
   - 本文は長いので、会話には全文を貼らない。代わりに次を報告する。
     - 記事の見出しの一覧
     - 入力から変えたところのうち、構成の変更・誤りの修正・補足を箇条書きで（文章の整え方は細かく挙げなくてよい）
     - 要確認の箇所、新しく作ったタグ
     - `npm run dev` で見た目を確認できること
   - ユーザーが全文を見たいと言ったら表示する。
   - 修正を頼まれたら、直して追加で commit する。
   - **push はしない。** ユーザーが自分のタイミングで行う。

## 書き方

### 構成は尊重し、文章は読みやすく整える

- **構成**: 節の分け方、論の進め方、話の順番といったユーザーの基本の構成は尊重する。「ここで強い仮定を入れてみる」のような、考えの道筋を示す部分も残す。順番を入れ替えたほうが明らかに読みやすいときだけ変えてよく、大きく変えるなら書く前に相談する。
- **文章**: ユーザーの文体をそのまま残す必要はない。殴り書きのメモでも、記事になるころには読みやすい文章になっているようにする。言い回しの書き換え、文の分割や統合、重複の削除は自由にしてよい（報告で一つずつ挙げなくてよい）。
- **事実や論理の誤り**: 直す。直し方に迷う場合や、ユーザーの意図とずれるかもしれない場合は、直したうえで報告で理由を添える。
- **補足**: 論理の飛躍を埋める一文、理解を助ける具体例や表を足してよい。足しすぎず、足したものは報告で挙げる。

### 形式

- **タイトル**: frontmatter の `title` が記事の見出し（h1）になる。本文に `#` の見出しは書かない。入力の先頭に大見出しがあれば、それを元にタイトルを決め、その下の見出しを `##` に繰り上げる。
  - タイトルは、話題と結論がひと目で分かるものにする（例: 「コインと看守のパズルは、コインの枚数が 2 の冪のときに限り解ける」）。
- **見出し**: 節は `##`、その中の小節は `###`。目次に出るので、見出しだけで流れが追える言葉にする。
- **冒頭**: 最初の見出しの前に、何の話で、結論は何かを数行で書く。入力にあればそれを使う。
- **長さ**: 上限はない。ただし同じことの繰り返しは削る。
- **数式**: `/note` と同じく LaTeX 記法にする（文中は `$...$`、独立した式は `$$` だけの行で挟む。数式ではない `$` は `\$`）。
  - 入力の Unicode の上付き・下付き文字（`2ⁿ`、`F₂` など）や、`*` で書いた演算は、LaTeX に直す（`$2^n$`、`$\mathbb{F}_2$`、`$\oplus$` など）。
  - 行列は、コードブロックではなく `\begin{pmatrix} ... \end{pmatrix}` で書く。
  - 見出しの中にも `$...$` を書いてよい（目次でも表示される）。
- 比較や対応関係は表か箇条書きに、コマンドや設定はコードブロックにする。強調（`**...**`）と引用（`>`）は使ってよい。

### frontmatter

```yaml
---
title: "タイトル"
date: YYYY-MM-DD
tags: [math, algebra]
long: true
---
```

- tags は `[a, b]` の1行形式、英小文字、1〜3個。既存のタグを優先し、新しく作ったら報告する。

## 正確さと著作権

- 証明や計算は、一通り自分で追って確かめる。確信が持てない記述は断定せず、報告で「ここは要確認」と伝える。
- サイトもリポジトリも public なので、本や問題集の文章をそのまま写さない。よく知られたパズルや定理を扱うのはよいが、文章は自分の言葉で書く。
- 試験名や問題番号などの出典は記事に書かない。
