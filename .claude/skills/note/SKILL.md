# 記事を書く

ユーザーが資格勉強などで新しく知ったことを、1本の短い記事にまとめる。ユーザーにかかる時間は **5分以内** を目標にする。

ユーザーの最初のメモ: $ARGUMENTS

## 手順

1. **聞き取り（質問は最大2〜3個、1回のメッセージにまとめて聞く）**
   - 何を勘違いしていたか、どこで迷ったか
   - 解説の要点（手元にあれば1〜2行で）
   - メモだけで十分に書けるなら、質問せずに次へ進んでよい。

2. **既存の記事とタグを確認する**
   ```sh
   # 既存タグ（多い順）
   grep -h '^tags:' src/content/notes/*.md | tr -d '[]' | sed 's/^tags://' | tr ',' '\n' | sed 's/^ *//;s/ *$//' | grep -v '^$' | sort | uniq -c | sort -rn
   # 既存記事のタイトル
   grep -H '^title:' src/content/notes/*.md
   ```
   - ほぼ同じ内容の記事があれば、新しく作るか既存の記事に追記するかをユーザーに聞く。

3. **記事を書く**
   - `npm run new -- <slug> "<タイトル>"` でファイルを作り、本文と tags を書き込む。
   - `npm run build` を実行して成功することを確かめる。失敗したら直す。

4. **commit する（push はしない）**
   ```sh
   git add src/content/notes/<slug>.md
   git commit -m "note: <タイトル>"
   ```
   - 完了したら、記事の本文をそのまま会話に表示する。
   - あわせて、要確認の箇所と新しく作ったタグがあれば一言添える。
   - 修正を頼まれたら、直して追加で commit する。
   - **push はしない。** ユーザーが自分のタイミングで行う。

## 記事のルール

- **1記事1トピック。** 関連する話は別の記事にしてタグでつなぐ。
- **長さ**: 本文は 400〜1000 字程度（1〜2分で読める量）。
- **構成**: 見出しは原則使わず、次の順で書く。
  1. 結論（1〜2文）
  2. なぜそうなるか（仕組み・理由）
  3. 例、または間違えやすいポイント。ユーザーの勘違いがあれば「〜と思いがちだが」の形で入れる。
- 比較や対応関係は表か箇条書きにする。
- コマンドや設定はコードブロックに入れる。
- **タイトル**: 内容がひと目で分かる文にする（例: 「TCP の3ウェイハンドシェイクは SYN → SYN/ACK → ACK」）。
- **slug**: 英小文字・数字・ハイフンだけ（例: `tcp-3way-handshake`）。

## frontmatter

```yaml
---
title: "タイトル"
date: YYYY-MM-DD
tags: [network, tcp]
---
```

- tags は必ず `[a, b]` の1行形式で書く（上のタグ一覧コマンドがこの形式を前提にしている）。
- 既存のタグを優先して使い、表記ゆれを作らない（`network` と `ネットワーク` を混在させない）。
- タグは英小文字。1記事あたり1〜3個。
- 新しいタグを作ったら、完了報告で伝える。

## 正確さと著作権

- 確信が持てない記述は断定しない。完了報告で「ここは要確認」と伝える。
- サイトもリポジトリも public なので、問題文・選択肢・解説文をそのまま写さない。内容は自分の言葉で要約する。
- 試験名や問題番号などの出典は記事に書かない。
